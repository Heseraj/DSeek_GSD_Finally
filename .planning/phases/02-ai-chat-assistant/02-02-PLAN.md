## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → POST /api/chat | Untrusted user message crosses here; body validated by ChatRequest (Pydantic) |
| LLM output (mock or live) → execution layer | The LLM's structured proposal is the second untrusted input; it must pass the same validation as manual trades |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | chat/service.py execution layer | high | mitigate | Prompt-injected proposals flow through the same `TradeRequest(**proposal)` + `execute_trade` validation as manual trades: unknown ticker → per-action failed error, insufficient cash/shares → per-action failed error, quantity Field(gt=0), ticker normalized uppercase-stripped; watchlist changes go through add_ticker/remove_ticker with the UNIQUE(user_id,ticker) backstop. Max damage = a simulated trade the validation already allows, bounded by available cash |
| T-02-04 | Tampering | ChatProposal parsing | medium | mitigate | LLM output is parsed with Pydantic `model_validate_json` (tolerant fallback lands in 02-03) — a malformed proposal can never reach the executor unparsed |
| T-02-05 | DoS | chat_messages persistence | low | accept | History is capped at 20 rows on load (cost guard); chat_messages rows grow linearly with use on a single-user local app — acceptable, no cleanup task needed |

No new packages are installed in this plan (dependencies landed in 02-01 with the T-02-SC gate); no API key is read or logged.
</threat_model>
